# 仕事のタスクと週間予定

このスキルは Codex での計画作業に使う。
既存のタスク管理サービスを尊重し、未選定ならローカルの週次メモで引き継ぐ。
Notion の接続や GitHub の利用だけを理由に管理基盤を決めない。

## 計画を再開する

1. リポジトリルートの `CLAUDE.local.md` があれば勤務条件と情報源を読む。
2. リポジトリ直下の `work-planning/開始日_終了日/` の `plan.md` と `todo.md`、その下の `days/YYYY-MM-DD/` の当日の `plan.md` と `todo.md` を読む。週は月曜〜日曜とし、両端の日付を `YYYY-MM-DD` で表す。
   対象週や当日分がなければ直近の記録を読み、未完了事項の継続要否と予定を確認して作る。過去の週や日の記録は残す。
3. 現在の日時とタイムゾーンを確認し、「今週」を具体的な日付で示す。
   メモの確認日以降に変化し得る期限、完了状態、予定を必要な範囲で更新する。

単発の一覧要求には一覧を返す。
週間計画を求められたら予定への割り当てまで行う。
質問や基盤選びを毎回最初からやり直さない。

## タスクの根拠と到達点をそろえる

- Slack のリンクは親投稿と返信を読む。
  ページ分割や取得範囲を確認し、延期、担当変更、承認、完了の返信まで追う。
  読めない範囲は明記し、取得失敗を「該当なし」に置き換えない。
- ローカルの指示、計画、作業差分と、関連 Issue の本文、コメント、PR を照合する。
  古いチェックリストや Issue の open 状態だけで進捗を断定しない。
- 同じタスクへの複数リンクは一件にまとめる。
  リンク先の内容とユーザーの呼び名が食い違う場合は対象を確かめる。
- 各タスクについて、今週の到達点、現在の状態、次の行動、期限、依存先、見積もり、根拠をそろえる。
  期限は「確定」「希望」「仮置き」「不明」を区別する。
  「テスト」「本番構築」「同期」「切替前確認」「本番切替」は別の到達点として扱う。
- ユーザーによる実績や対象範囲の訂正を反映する。
  外部情報と矛盾が残る場合は、出典と確認日時を添えて不明点を残す。

## 不明点は一つずつ聞く

読み取りで分かる進捗や構成は先に調べる。
質問するのは期限、優先順位、完了条件、参加範囲など、本人の判断が必要な事項に絞る。
回答に依存しない調査と報告準備を先に済ませ、応答の最後に、計画への影響が大きいものから `request_user_input_async` で一問ずつ聞く。
一回の呼び出しに質問を一つだけ入れ、同じ質問をチャットに重ねない。
質問した後はツール操作や進捗説明を重ねず、回答を待つ。
回答を要する割り当ては保留し、待機中に同じ質問を繰り返さない。
経過時間や無回答を合意と扱わない。
ツールが利用できない環境では、その旨を伝えてチャットで一問ずつ聞く。

## カレンダーから使える時間を出す

1. 対象アカウントを識別し、アカウントごとにカレンダー一覧を確認する。
   primary が空でも、NASCA などの副カレンダーや購読カレンダーを調べる。
   接続プロフィールの取得成功と、予定の読取成功は分けて報告する。
   接続 ID や使用ツールは現環境から取得し、過去の値を決め打ちしない。
2. 対象週を現地時刻の月曜日から翌月曜日の手前まで取得し、ページ分割を確認する。
   読取制限があれば予定の網羅性を保証しない。
3. 同じ NASCA 予定が複数のカレンダーにある場合は、タイトル、時刻、参加者、元 ID などで照合して一度だけ数える。
   終日表示と時間指定の重複、同僚の休暇、任意参加も判別する。
4. 勤務時間、昼休憩、実際の参加時間、移動や準備、今日の経過済み時間を差し引く。
   面談枠全体の人数割りは、順番と一人分の長さが未確認なら仮置きと明記する。
5. ながら聞きが許された会議には中断しやすい軽作業を候補にする。
   集中作業や本番操作に使える時間と同じには数えない。

## 見積もって割り当てる

過去の実績があれば、質問する前に [実績と作業履歴の扱い](references/evidence.md) に従って調べる。
見積もりには根拠と幅を付け、準備、本作業、確認、外部からの返答待ちを分ける。
開催時間を準備時間に流用せず、別作業を一つの見積もりに混ぜない。

期限が早い作業と、他者への依頼が必要な作業から配置する。
依頼後の待ち時間には独立した作業を置き、承認や同期完了を前提とする工程には条件を付ける。
実行可能性を判断するには、タスクを時間枠に割り当て、重複と依存関係、休憩、予備時間を点検する。
一日ごとの候補だけを並べた段階では「日別の仮案」と表示する。
見積もりや参加時間が未確定なら、「今週に収まる」と断定しない。
収まらない場合は、後ろへ送る候補か到達点を縮める候補を示す。

一覧はタスク名、今週の到達点、期限、次の行動を中心に短く返す。
週間計画では日付と時間枠、作業名を示し、未確定条件と依頼待ちを添える。
根拠へのリンクを付け、番号だけで作業を呼ばない。

## 決定を引き継ぐ

リポジトリ直下の `work-planning/` に週ごとの `開始日_終了日/` (例: `2026-10-19_2026-10-25/`) を作り、週間計画を `plan.md`、週全体の一覧を `todo.md` に置く。
その下の `days/YYYY-MM-DD/` に当日の詳細 `plan.md` と一覧 `todo.md` を置く。
週の一覧は期限と今週の到達点、日の一覧は日付と取り組む順番を短いチェックリストで示し、進行中と完了を区別する。
詳細な根拠や見積もりは対応する `plan.md` へリンクし、計画や進捗の変更時は日次と週次の対応箇所に反映する。
本人が編集した項目も読み込み、削除や完了を推測で上書きしない。
「話題」「覚えておくだけ」という依頼は話題メモとして保存し、調査や準備タスクに拡張しない。
日や週が変わったら未完了の継続要否を確かめ、過去分を残して新しい日や週のファイルを作る。
個人の仕事内容を含む `work-planning/` 全体を Git 管理外にする。

継続的な計画では、週と日の `plan.md` の対応箇所を決定や訂正に合わせて更新する。
メモには確認日、タスクと出典、到達点、状態、期限の確度、見積もりの根拠、次の行動、未回答の一問、予定案を残す。
確定事項と提案中の予定を区別し、完了は実行の根拠がある場合に付ける。
進捗報告では作成、精査、commit、実環境への反映を区別し、本人報告と自分で検証した範囲を明記する。
終了と追跡不要が報告された委譲先には、追加指示なしに返信、監視、再実行をしない。
次週には未完了の継続要否と持ち越す理由を確かめる。

安定した勤務条件と参照先は `CLAUDE.local.md`、日付や週に限定した判断は `plan.md` に置く。
個人情報を含む両方の保存先が Git 管理外であることを確認する。
認証情報と会話ログ全文は保存せず、判断に必要な要約と出典だけを残す。

## 実行に進む場合

計画の了承から、Slack 送信、Issue 作成、予定登録、本番操作までの許可を推定しない。
既に明示された実行指示は尊重し、対象、内容、実行先を確かめて進める。
外部に登録する場合は既存項目を照合して重複を避け、実行結果を読み戻す。

稼働記録の依頼には利用可能な `worklog`、`worklog-operation`、`worklog-find` を必要に応じて使う。
過去分の登録とエージェントへの履歴調査依頼の注意点は [実績と作業履歴の扱い](references/evidence.md) を読む。
タスクの計画や調査を始めただけでは、計測の開始や停止を行わない。
`stop` 実行済みとの報告を受けたら二重に停止しない。並列作業の開始を理由に、別作業の計測を停止や切替しない。
