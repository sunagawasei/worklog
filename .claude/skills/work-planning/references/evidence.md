# 実績と作業履歴の扱い

## 作業時間の見積もり

worklog の同名または類似タスクを探し、タグと作業内容を確認する。
必要ならユーザーが指定したプロジェクトのセッション履歴を調べる。
履歴は関連箇所の時刻と操作だけを取り出し、全文を出力しない。
Slack や作業履歴に認証情報が含まれる場合も、回答や引き継ぎ文書には転記しない。

以下の時間を混同しない。

| 種類 | 読み取れること |
| --- | --- |
| worklog の開始から停止 | その名前とタグで計測した時間 |
| 会話の依頼から確定 | 待機や別作業を含む経過時間 |
| ファイルの作成や更新 | 成果物が書かれた時刻 |
| 人の実作業時間 | 上記だけでは通常確定できない |

ログ間のずれがあれば、どの区間を測った値かを示す。
無通信の時間を任意の閾値で引いて「正確な実作業時間」にしない。
無関係な修正、予約、待機、終了処理を含むかを点検する。
見積もりとして採用する値は、測定値と予備時間を分けて記録する。
一件の実績から、今後の同種作業をすべて同じ時間に固定しない。

## 過去の稼働記録

カレンダーの予定時間は実績の根拠にしない。
本人が訂正した参加時間を優先する。
既存のタスク名とタグを再利用し、対象日の timeline と現在の計測状態を確認する。
`new` や `switch` は計測中の作業を停止し得るため、過去分の追記に流用しない。

利用できる CLI が過去分の追加や訂正を扱えるか、現在のヘルプと操作スキルを確認する。
ファイル編集が必要なら対象を限定し、上書きしないバックアップを取り、既存区間や重複を確認する。
依頼された履歴だけを変更し、timeline で時刻、重複、合計を再確認する。
現在の計測はユーザーの停止指示なしに止めない。

## 別のエージェントへの履歴調査依頼

委譲を求められた場合に、利用可能な `agmsg` または `handoff` のスキルを読む。
ユーザーが指定したプロジェクト、モデル、調査範囲を渡し、時刻の根拠と不明点を回答させる。
読み取りに必要なディレクトリを確認し、制限エラーと「履歴が存在しない」を区別する。
対処には必要な範囲のアクセスや認証情報を除いた抜粋を使い、恒久的な権限設定の変更に広げない。

headless 実行では、起動時のメッセージが実際に配送されるかを現在の実装で確認する。
起動準備の完了は調査結果の受信を意味しない。
バックグラウンドの子プロセスが呼び出し元の終了時に停止する環境では、起動、依頼、返信待ちを同じ生存中の実行に保つ。
短い間隔で結果を確認して進捗を伝え、タイムアウト時は状態を確認してから再試行する。
同じ調査を重複起動せず、結果を受け取ったら根拠の時刻を抜き取り確認する。
